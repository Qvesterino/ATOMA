CORE METHOD: _applyCorruptionGlyphDimming()
──────────────────────────────────────────────

Location: _AtomaGlyphSystem4_0.js, lines 1474-1558

Signature:
  _applyCorruptionGlyphDimming(glyphGroup, nodeId, context)

Parameters:
  - glyphGroup: THREE.Group containing glyph meshes
  - nodeId: String identifier for node
  - context: Object with .corruption property (0-1)

Process:
  1. Extract corruption value from context
  2. Check if corruption >= activeThreshold (0.65)
  3. Calculate dimming factor: 1.0 → 0.25 (linear)
  4. Apply opacity reduction to all child materials
  5. Apply emissive intensity reduction
  6. Apply progressive desaturation (>= 30% progress)
  7. Store base values for frame-to-frame consistency

Output:
  - Modified glyphGroup.userData.corruptionDimmingActive (boolean)
  - Modified glyphGroup.userData.corruptionDimmingFactor (number)
  - Modified all child material opacity/emissive/color

CONFIGURATION OBJECT
──────────────────────

Default Values:
  {
    activeThreshold: 0.65,      // Start dimming at this corruption
    maxDimmingThreshold: 0.85,  // Reach full dim at this corruption
    minOpacityFactor: 0.25      // Minimum opacity at max corruption
  }

Customization:
  glyphSystem.setCorruptionDimmingConfig({
    activeThreshold: 0.50,      // Example: start earlier
    maxDimmingThreshold: 0.75,  // Example: reach full dim sooner
    minOpacityFactor: 0.10      // Example: fade more aggressively
  });

Query:
  const config = glyphSystem.getCorruptionDimmingConfig();

DIMMING FORMULA
────────────────

Given:
  corruption = node corruption value (0-1)
  activeThreshold = 0.65
  maxDimmingThreshold = 0.85
  minOpacityFactor = 0.25

Calculate:
  if corruption < 0.65:
    dimmingFactor = 1.0  (no dimming)
  else:
    dimmingRange = 0.85 - 0.65 = 0.20
    corruptionProgress = min((corruption - 0.65) / 0.20, 1.0)
    dimmingFactor = 1.0 - (corruptionProgress * (1.0 - 0.25))
                  = 1.0 - (corruptionProgress * 0.75)

Apply:
  finalOpacity = baseOpacity * dimmingFactor

Examples:
  corruption = 0.65  → dimmingFactor = 1.0    → opacity = 100%
  corruption = 0.70  → dimmingFactor = 0.625  → opacity = 62.5%
  corruption = 0.75  → dimmingFactor = 0.5    → opacity = 50%
  corruption = 0.85  → dimmingFactor = 0.25   → opacity = 25%
  corruption = 0.90  → dimmingFactor = 0.25   → opacity = 25% (capped)

OPACITY REDUCTION BEHAVIOR
────────────────────────────

Each frame:
  1. Check if child.userData.baseOpacityBeforeDimming exists
  2. If not, store current child.material.opacity
  3. Apply: child.material.opacity = baseOpacity * dimmingFactor
  4. Result: Smooth linear fade from 100% to 25%

Lazy initialization ensures:
  - Base value stored once (first frame)
  - Reused every subsequent frame
  - Smooth transitions even with rapid corruption changes

EMISSIVE INTENSITY REDUCTION
──────────────────────────────

Same pattern as opacity:
  1. Store base emissiveIntensity on first frame
  2. Apply: intensity = baseIntensity * dimmingFactor
  3. Result: Dimmed glyphs lose their glow

Creates visual consistency: dark glyphs appear less radiant

DESATURATION EFFECT
─────────────────────

Applied when corruptionProgress > 0.3 (approximately >= 0.71 corruption):
  1. Calculate desaturation amount: progress * 0.15 (0-15%)
  2. For each color component:
     - Calculate luminance: (r + g + b) / 3
     - Create gray color: Color(luminance, luminance, luminance)
     - Lerp: color.lerpColors(original, gray, desaturation)
  3. Result: Progressive shift toward grayscale

Creates semantic: System "losing vibrancy/health" as corruption increases

INTEGRATION POINT
──────────────────

COMPOUND EFFECTS
─────────────────

1. Opacity Dimming:
   - Primary effect: opacity * dimmingFactor (100% → 25%)
   - Smooth linear progression
   - Creates fade effect

2. Emissive Reduction:
   - Secondary effect: emissiveIntensity * dimmingFactor
   - Glyphs lose radiance
   - Complements opacity dimming

3. Desaturation:
   - Tertiary effect: color → gray (0-15%)
   - Applies only at high corruption (>= 0.71)
   - Creates "sickness" visual language

Combined effect: Glyphs become dim, dark, and washed out at high corruption

INTERACTION WITH SYNERGY REVEAL
─────────────────────────────────

Scenario 1: High Synergy, Low Corruption
  Synergy reveals glyph (≥ 0.75)
  → Glyph brightened and boosted
  → Result: Bright, visible glyph

Scenario 2: High Synergy, High Corruption
  Synergy reveals glyph (≥ 0.75)
  → Corruption dimming applied AFTER
  → Dimming multiplier applied to boosted opacity
  → Result: Dim glyph (corruption wins)
  Metaphor: "Even meaning can't survive system failure"

DESIGN DECISIONS & RATIONALE
═══════════════════════════════════════════════════════════════════════════════

WHY 0.65 THRESHOLD?
─────────────────────
✓ Matches corruption visual deformation (Session 66)
✓ Creates coordinated feedback: node glyphs dim + links deform
✓ Established convention from previous sessions
✓ Provides early visual signal of system trouble

WHY 0.85 MAX DIMMING THRESHOLD?
──────────────────────────────────
✓ Extends dimming range to 0.20 (matches Session 66 visual range)
✓ Provides gradual fade rather than sudden dim
✓ Aligns with session 66/67 design philosophy
✓ Creates clear visual progression from "failing" to "collapsed"

WHY 25% MINIMUM OPACITY?
──────────────────────────
✓ Glyphs remain faintly visible (suggests "system still existing")
✓ Allows future recovery animation from collapsed state
✓ Maintains visual continuity (never completely invisible)
✓ Semantic: System "barely alive" not "dead"

WHY APPLY AFTER SYNERGY REVEAL?
─────────────────────────────────
✓ Corruption more critical than synergy (system failure > connection quality)
✓ Visual priority: Corruption dominates when both active
✓ Semantic: When system breaks, meaning is lost
✓ Enables "override" visual language

WHY INCLUDE DESATURATION?
──────────────────────────
✓ Enhances dimming effect with "sickness" language
✓ Synergy glyphs vibrant (healthy); corrupted glyphs gray (sick)
✓ Compound effect stronger than opacity alone
✓ Thematic: Color and vibrancy = health

WHY LAZY INITIALIZATION OF BASE VALUES?
─────────────────────────────────────────
✓ Ensures smooth transitions even with rapid corruption changes
✓ Base value stored once per glyph child (efficient)
✓ Reused every frame (no recalculation)
✓ Prevents drift or accumulation errors
