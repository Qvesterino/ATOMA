# P0.3 LinkRendererConduit Performance Audit

**Dátum:** 2026-04-16  
**Súbor:** `LinkRendererConduit.js` (266KB, ~6000 riadkov)  
**Súvisiace:** `LinkStateVisualLanguageIntegration.js`, `LinkBeadSystem.js`, `LinkBeadTrailSystem.js`

---

## Exekutívny verdikt

LinkRendererConduit je **najzložitejší runtime súbor** v ATOMA. Má už existujúcu LOD a cadence infraštruktúru, ale niekoľko kritických oblastí stále spôsobuje zbytočné GPU/CPU zaťaženie.

**Rating: 7/10** — Má solídne základy, ale potrebuje cieľavé optimalizácie.

---

## Už existujúca infraštruktúra ✅

1. **Cadence gating:** `_acc30`, `_acc10`, `run30`, `run10` — separuje 60Hz od 30Hz a 10Hz ✅
2. **Heavy link selection:** `_selectHeavyLinks(list, camera, heavyDistance, maxHeavyLinks)` — limituje heavy efekty na najbližších 10 liniek ✅
3. **LOD levels:** `_getLinkLODLevel(start, end)` — vracia 0/1/2 podľa vzdialenosti ✅
4. **Cached Frenet frames:** `state.__cachedFrenetFrames` — cachuje výsledok ✅
5. **Backbone freeze:** `state.__backboneFrozen` — môže zmraziť geometriu ✅
6. **Distance LOD visual scale:** `lodVisualScale = lod >= 2 ? 0.45 : 1.0` ✅
7. **Braid rebuild gating:** `braidRebuildReady`, `braidMoved`, `braidRadiusChanged` ✅
8. **Skin rebuild gating:** `skinMoved`, `skinRadiusChanged` ✅

## Nájdené problémy a návrhy

### 🔴 HIGH: Per-frame TubeGeometry allocation v strand update

**Lokácia:** Riadok ~4178  
**Problém:** `new THREE.TubeGeometry()` sa volá pri každom rebuild strandu. TubeGeometry vytvára nový BufferGeometry + CatmullRomCurve3 vnútorne. Pri 10+ heavy linkách pri 30Hz to môže byť 300+ TubeGeometry alokácií za sekundu.

```javascript
if (mesh.geometry) mesh.geometry.dispose();
mesh.geometry = new THREE.TubeGeometry(
    new THREE.CatmullRomCurve3(points),
    segments,
    this.config.strandRadius,
    this.config.radialSegments,
    false
);
```

**Rovnaký problém na riadku ~4274 pre skin:**
```javascript
if (skin.geometry) skin.geometry.dispose();
skin.geometry = new THREE.TubeGeometry(mainCurve, segments, skinRadius, 8, false);
```

**Návrh:**
- Pre bunkrové rúry: použiť `BufferGeometry` s pre-allocovaným `Float32Array` a aktualizovať len `position` attribute. `TubeGeometry` je len wrapper okolo `BufferGeometry` — môžeme replikovať jeho logiku a reuseovať buffer.
- **Quick win:** Pridať časový threshold na rebuild — ak sa link nehýbe a metriky sa zmenili len marginálne, skip rebuild.

### 🔴 HIGH: Per-strand uniform writes bez deduplikácie

**Lokácia:** Riadky ~4070-4115, ~4289-4340  
**Problém:** Každý strand mesh dostáva ~12 uniform writes pri 30Hz:
- `uTime`, `uCorruption`, `uNetworkStress`, `uLocalLoad`, `uWaveDirection`, `uWaveLength`, `uWavePhaseOffset`, `uSegmentCount`, `uHarmony`, `uSynergy`, `uStress`, `uLoad`, `uDesaturation`, `uLOD`, `uLinkBirthIntensity`, `uLinkRemovalIntensity`

Pri 5 strandoch × 12+ uniforms × 30Hz = **1800+ uniform writes za sekundu na link**.

Pre 10 heavy links = **18,000+ uniform writes za sekundu**.

**Návrh:**
- Použiť `onBeforeRender` callback na meshoch — zapísať uniformy len keď je mesh viditeľný a blízko kamery.
- Zápis `uTime` len raz za frame na zdieľaný material, nie per-strand.
- Skontrolovať, či niektoré strandy zdieľajú materiál — ak áno, zapísať uniformy len raz.

### 🟡 MEDIUM: computeFrenetFrames nie je dostatočne cachovaný

**Lokácia:** Riadok ~3965  
**Problém:** `computeFrenetFrames` sa volá pri každom `geometryTick`. Ten beží pri 10Hz pre non-frozen linky. Pre 30+ liniek je to 300+ Frenet frame kalkulácií za sekundu.

**Existujúca ochrana:** Frames sú cachované v `state.__cachedFrenetFrames`, ale len na jeden frame — ďalší geometryTick ich prepíše.

**Návrh:**
- Pridať threshold: prepočítať Frenet frames len ak sa link endpointy posunuli o viac ako X jednotiek.
- Pre stabilné/statické linky: cachovať na dlhšie obdobie (napr. 2-3 sekundy).

### 🟡 MEDIUM: Dock ring a dock spray update pri 60Hz

**Lokácia:** Riadok ~3865-3898  
**Problém:** Dock ring a dock spray sa aktualizujú pri každom heavyTick (30Hz), ale sú sekundárne vizuálne prvky, ktoré by mohli bežať pri 15-20Hz.

```javascript
if (heavyTick) {
    if (runDockEffects && state.dockRing) {
        // ... dock ring update
        state.dockSpray.update(visualTime);
    }
}
```

**Návrh:**
- Oddeliť dock ring update od heavyTick.
- Pridať vlastný cadence bucket pre dock efekty (napr. 20Hz).

### 🟡 MEDIUM: Source injection update bez LOD gating

**Lokácia:** Riadok ~3898  
**Problém:** `state.sourceInjection.update()` beží pri heavyTick bez ohľadu na LOD.

```javascript
state.sourceInjection.update(visualTime, injectionAnchor, linkDir, injectionFlow);
```

**Návrh:**
- Pridať LOD kontrolu — pre ďaleké linky (LOD 2+) skip source injection.

### 🟢 LOW: clone() alokácie v update loope

**Lokácia:** Viaceré miesta  
**Problém:** `sourceCenter.clone()`, `linkDir.clone()` vytvárajú nové Vector3 objekty v update loope.

```javascript
const sourceInjectionOrigin = sourceCenter.clone().addScaledVector(linkDir, sourceRadius * 0.06);
const injectionAnchor = sourcePortPos.clone();
```

**Návrh:**
- Použiť pre-allocované scratch Vector3 objekty (už existujú: `_linkWorldPosA`, `_linkWorldPosB`, `_lodMidpoint`).

### 🟢 LOW: Beads update bez LOD skip

**Lokácia:** Riadok ~4463  
**Problém:** `state.beads.update()` beží pri heavyTick, ale beads môžu byť skipované pre vzdialené linky.

```javascript
state.beads.update(visualDelta, (bead) => { ... }, lodAllowsParticles);
```

**Existujúca ochrana:** `lodAllowsParticles` sa už používa ako parameter, ale callback sa stále volá.

## Optimizačný plán

### Fáza 1: Quick wins (nízke riziko, vysoký dopad)

| # | Optimalizácia | Typ | Odhadovaný zisk |
|---|--------------|-----|-----------------|
| 1 | Deduplikácia uniform writes — `uTime` zdieľaný | CPU | ~20% uniform writes |
| 2 | Dock ring/spray → vlastný cadence (20Hz) | CPU | ~33% dock update calls |
| 3 | Source injection → LOD gating | CPU/GPU | Skip pre far linky |
| 4 | Nahradenie clone() za scratch vectors | GC | Eliminácia per-frame alokácií |

### Fáza 2: Stredné zmeny (stredné riziko, vysoký dopad)

| # | Optimalizácia | Typ | Odhadovaný zisk |
|---|--------------|-----|-----------------|
| 5 | TubeGeometry → reusable BufferGeometry | CPU/GPU/GC | Eliminácia ~300 alloc/s |
| 6 | Frenet frames distance threshold | CPU | ~50% Frenet calls pre stabilné linky |
| 7 | Material sharing pre strandy rovnakej linky | CPU/GPU | ~80% uniform writes reduction |

### Fáza 3: Architektonické (vyššie riziko, najvyšší dopad)

| # | Optimalizácia | Typ | Odhadovaný zisk |
|---|--------------|-----|-----------------|
| 8 | Link budget systém: hero/near/mid/far | CPU/GPU | Kompletný frame budget control |
| 9 | Instanced rendering pre vzdialené linky | GPU | ~90% draw calls pre far linky |
| 10 | GPU-driven strand update (compute shader) | GPU | Offload CPU strand work |

---

## Odporúčaný postup

1. **Začať s Fázou 1** — quick wins, minimálne riziko, okamžitý benefit
2. **Pokračovať s Fázou 2** — stredné zmeny, vyžaduje testing
3. **Fáza 3** — až po overení, že Fázy 1 a 2 priniesli merateľný benefit

---

## Merateľné ciele (P0.3 "Hotovo keď")

- [ ] Frame time pri 20+ linkách nepresahuje 16ms (60fps)
- [ ] Zero per-frame TubeGeometry alokácií v stabilnom stave
- [ ] Uniform writes redukované o minimálne 30%
- [ ] Frenet frames prepočítavané len pri pohybe linku
- [ ] Dock efekty bežia pri 20Hz, nie pri 30Hz
- [ ] Žiadne per-frame `new Vector3()` alokácie v update loope
