# ATOMA Overview

ATOMA is a browser-native game about stabilizing a living AI network before it loses coherence.

It is not only AI-themed. It is intentionally being built as an **AI-native, agent-evolvable game system**: a project that can continue advancing through human-directed product taste and agent-executed engineering work.

---

## Product Identity

The player fantasy is:

- enter a living, unstable networked world
- build bonds between nodes
- turn scattered structure into a coherent lattice
- open a stabilization surge
- prevent collapse long enough to hold the world together

ATOMA should feel:

- alive
- intelligent
- systemic
- atmospheric
- readable under pressure

The game is not meant to read as a sterile metrics sandbox. Metrics exist to support the feeling of stabilizing a conscious machine-world.

---

## Current Release Slice

The current product slice is centered on:

- the **Stabilizer** fantasy loop
- `Network Time` as the score-pressure axis
- `REWIND` as the first major stabilization payoff
- `WON` as stabilization achieved, not a generic score clear

Release-priority worlds are:

- `Quantum Island`
- `Dream Desert`

Other worlds still exist in code and may evolve further, but they are not the primary onboarding or release-proof slice.

---

## Current Player-Facing Pillars

ATOMA currently relies on these readability and identity layers:

- build-state readability:
  - `VOLATILE SURGE`
  - `STABILIZED LATTICE`
  - `FRAGILE EXPANSION`
  - `COLLAPSE DRIFT`
- first-run guided onboarding
- run identity packages and world-state selection
- curated signature setpieces
- procedural audio-reactive identity
- adaptive browser-performance discipline
- polished pause/resume and soft-failure UX

The direction is not “more systems for their own sake”.
The direction is stronger authored identity, clearer decisions, and better browser execution quality.

---

## AI-Native Doctrine

ATOMA is expected to keep evolving through a hybrid model:

- the human defines meaning, direction, and taste
- agents extend, refine, harden, and document the system
- the documentation layer must make that handoff safe

That means the project should be documented so that a new agent can rapidly recover:

- what the game is
- what the current release slice is
- what the canonical runtime authorities are
- what should be improved next without inventing a second project inside the repo

This doctrine is a design constraint, not marketing language.

---

## Direction

The near-term direction for ATOMA is:

- deepen meaningful gameplay decisions
- strengthen world authorship and memorable setpieces
- keep the browser runtime performant and graceful under pressure
- preserve subsystem autonomy and canonical authority ownership
- make each new pass legible to future agents through disciplined documentation

If a future change improves spectacle but weakens readability, authority discipline, or browser stability, it is the wrong change.
